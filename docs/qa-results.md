## 边界检查

测试方式：直接调用输入处理 / 校验函数 + 两个真实分页（不是逐个鼠标输入）。

**1. 负数 / 超过上限的输入**
- 通过：退款金额不填 / 负数 / 非数字被挡（项目退款、持有批次退款）；持有批次退款超过当初实付被挡，0 可以；诊所设定面诊费负数 / 小数 / 文字 / 超过 1 亿被挡，占位倒计时 0 / 121、未到店判定 4 分钟、时段上限 0 / 51、提醒小时 73 都被挡；项目价格负数 / 空被挡；使用持有项目的数量被夹在剩余次数内（`qtyClamp`）。
- 需修正：折扣框填 `0` / `-5` / `1e2` 都变成 1，即「0.1折」，结算金额只有原价的 1%（870,000 → 8,700）；填 150 → 当作不打折（100）；应不应该拒绝 0 / 负数？
- 需修正：本地选购的数量没有上限，填 999999 照样接受（870,000 × 999,999 ≈ 8.7 × 10⁹），0 / 负数 / 文字都变成 1。
- 观察：KR 选施术时间的下拉列出 08:00～20:00，选营业时间外会被挡「施术时间要在医院营业时间内」，但选项不该给。

**2. 刚好卡在时间点上**
- 需修正（未到店 30 分钟）：案件的预约时间已过 35 分钟，等 4 秒仍是「待访问」；`markNoShow(auto)` 只被演示按钮「模拟时间超过 30 分钟」调用，没有任何定时器真正自动判定（日历上的倒计时到 0 只写「已超时」）。状态机总览第 13 节写的是「过预约时间 30 分钟未点到访，系统自动判定」。
- 需修正（施术前 2 周）：`isWithin2WeeksOfToday` 用 `new Date('YYYY-MM-DD')`（UTC 零点）减 `TODAY_DATE`（浏览器本地零点），刚好 14 天这一天的结果取决于浏览器所在时区（本机 UTC+9：距今 14 天 = 可改期，13 天 = 不可改；换成 UTC-5 的浏览器会差一天）。规则「施术前 2 周截止」应按诊所 / 页面时区算。
- 通过（活动最后一天）：结束日当天仍「进行中」，次日「已结束」，开始日前「未开始」（`promoStatusOf`）；过期自动恢复原价。
- 通过（占位）：占位倒计时按分钟设定，剩 5 分钟提示、到点消失（前面 C 模块）。

**3. 两个分页同时操作同一案件**
- 需修正：存档是「整个诊所分区最后写入者覆盖」，没有版本号 / 合并。实测：IN 分页卡住 9 秒（模拟页面无响应），期间 KR 分页往同一案件写了一条 Timeline 并成功保存；IN 分页恢复后保存自己的改动，KR 的那条记录被覆盖丢失（IN 最终 Timeline 只有自己的「RACE-SEED」，没有 KR 的「RACE-KR」）。平时 storage 事件几十毫秒就同步，窗口很小，但页面失去响应（后台降速、弹窗卡住）时会丢数据。
- 通过：两个分页各自登录（sessionStorage）、同一份共用数据即时同步，弹窗打开时延后重画、关闭后补刷新（前面各模块都在用）。

**4. 全站数据一致性**（`dev/audit-hours.js` + 财务 / 持有批次 / 案件号检查脚本，覆盖 3 家诊所 49 个案件、26 张结算单、14 个持有批次）
